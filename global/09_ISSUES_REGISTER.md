| DEV-STACK-1 | SRS §3.3 fixes Spring Boot/Java 21 as the backend framework; this build uses Go instead. | ✅ resolved | Deliberate substitution for the learning goal and to keep raw SQL natural (no ORM fighting it). Every *behavioral* SRS requirement (REST/JSON, MySQL 8, stateless, JWT, BCrypt, atomic stock via stored procedure) is preserved — see `01_TECH_STACK.md` deviation note. Confirm with course staff whether the SRS itself should be re-versioned to v1.2 reflecting this, or left as-is with this register entry as the record. |
| SEC-RLS-1 | MySQL 8 has no Row-Level Security, unlike the Postgres reference architecture this spec system's structure was borrowed from. | ✅ resolved | Compensating control: least-privilege DB role + mandatory ownership predicate in every query's `WHERE` clause, code-review-enforced. See `02_SECURITY_BASELINE.md` §6. |
| DB-DENORM-1 | Whether `product_variant`'s In-Stock/Out-of-Stock status should be a stored column or derived. | ✅ resolved | Derived (`fn_is_variant_in_stock`), per REQ-5.4 — avoids a flag that can drift from the real quantity. `07_SQL_DATABASE_STANDARDS.md` §1. |
| ARCH-DI-1 | Whether to use a Go DI framework (`wire`/`fx`) or manual wiring. | ✅ resolved | Manual wiring in `cmd/api/main.go`. Revisit only if the composition root stops being readable by hand as module count grows. `06_ENGINEERING_STANDARDS.md` §3. |
| OQ-2 | Backend/frontend as one monorepo or two repositories? | ✅ resolved (2026-09-02) | Two repositories: `brightbuy-backend`, `brightbuy-frontend`. `openapi.yaml` (outside both) is the sync contract across the split. `01_TECH_STACK.md` §2. |
| RBAC-1 | SRS ER diagram's `ROLE` table has 4 fixed roles with no permission model; SRS §2.3 implies a 5th actor (Store/Order Manager) with no defined permissions. | ✅ resolved (2026-09-02) | 5 roles (`CUSTOMER, WAREHOUSE_STAFF, ORDER_MANAGER, MANAGER, ADMIN`) plus a runtime-editable `permission`/`role_permission` schema — a deviation from the delivered ER diagram, made deliberately for a more modular/loosely-coupled authorization model. `ADMIN` is a code-level unconditional bypass so it can't be locked out. `00_OVERVIEW.md` §2, `02_SECURITY_BASELINE.md` §1, `07_SQL_DATABASE_STANDARDS.md` §1a. |
| IMG-1 | SRS implies product images (§6.2) but the ER diagram has no image entity and Phase 1's original plan (`01_TECH_STACK.md` v1) deferred to seed-only placeholders. | ✅ resolved (2026-09-02) | Real upload pipeline: new `product_image` table (beyond the ER diagram), S3-compatible storage (MinIO locally, S3/R2 free tier in prod) behind an `ImageStorage` port, presigned-URL upload gated by the new `catalog:image:write` permission. `01_TECH_STACK.md` §1, `07_SQL_DATABASE_STANDARDS.md` §1a, `02_SECURITY_BASELINE.md` §4, `08_THREAT_MODEL.md` T-16. |
| SQL-BUG-3 | `trg_order_status_history` (`07` §4) only fires on `UPDATE order` — an order's first status (`Confirmed`, set by `sp_place_order`'s `INSERT`) would never get a history row, so REQ-8.5's "every status change" would be missing its own starting point. Found while drafting `08-order-tracking-status` and tracing the trigger's actual coverage. | ✅ resolved (2026-09-04) | `sp_place_order` now also inserts the initial `order_status_history` row directly (`changed_by_user_id` NULL — system-created, same pattern as `SQL-BUG-2`'s stock_movement fix). `order_status_history`'s DDL ships with `04-checkout-orders` (needed there first, same reasoning as `stock_movement`); `08-order-tracking-status` adds the two triggers and `sp_cancel_order` that operate on it afterward. |
| SQL-BUG-2 | `sp_place_order` decremented stock without writing a `stock_movement` row — REQ-5.5 requires *every* increase/decrease logged with the related order, not just manual staff adjustments. `sp_cancel_order`'s restock had the same gap. Found while drafting `06-inventory-stock` and tracing where `stock_movement` was actually written from. | ✅ resolved (2026-09-04) | Both procedures now insert a `stock_movement` row (`related_order_id` set, `acting_user_id` NULL for the system-driven placement decrement, set to the cancelling staff member for the cancellation restock). `07_SQL_DATABASE_STANDARDS.md` §3.1/§3.3. `stock_movement`'s DDL itself ships with `04-checkout-orders` (needed there first, since `sp_place_order` writes to it), reused — not redefined — by `06-inventory-stock`. |
| SQL-BUG-1 | `fn_estimate_delivery_days` (`07_SQL_DATABASE_STANDARDS.md` §5), as originally drafted, ignored delivery mode and would have run the Main/Other-City rule (and `fn_classify_city(NULL)`) for Store Pickup orders too — REQ-6.6 says Pickup uses a completely different rule and collects no destination city. Found while drafting `04-checkout-orders`. | ✅ resolved (2026-09-04) | Function signature now takes `p_delivery_mode`; branches to the 0/+3-day pickup rule (TBD-3 assumption) before ever touching city classification. `sp_place_order` (§3.1) updated to pass the mode and compute the estimate once into a variable instead of calling the function twice. |
| DB-ERD-1 | `00_OVERVIEW.md` originally claimed BrightBuy's roles "match the ER diagram's `ROLE` table" — inaccurate. SRS Figure B.1 (Appendix B.1) is explicitly scoped to "the main entities" (`Category, Product, Customer, Order, ProductVariant, OrderItem, Delivery, Payment`) and depicts no authentication/role/staff entity at all. | ✅ resolved (2026-09-04) | Corrected in `00_OVERVIEW.md` §2. `user_account`, `customer`, `staff_profile`, `role`, `permission`, `role_permission` are designed from the SRS's *text* requirements (REQ-2.1–2.8), not the diagram, since the diagram simply doesn't cover this part of the schema — not a deviation from it, just outside what it depicts. Full DDL: `02-auth/plan.md` §2. |
