# 07 — SQL & Database Standards

This is the DBMS-module-critical document. It fixes: no ORM (raw SQL only), the injection-prevention
policy, and — the graded core of this project — how stored procedures, triggers, functions, views,
window functions and indexing are used, and *why each one earns its place* rather than being bolted on
to tick a syllabus box. Inherited by every feature; a feature's `plan.md` cites the objects here it
uses and adds only what's new.

All DDL lives in `db/migrations/` as numbered `golang-migrate` file pairs (`NNNN_description.up.sql` /
`.down.sql`). Nothing here is hand-applied to any environment.

---

## 1. Schema conventions

- **Engine:** InnoDB everywhere (transactions, foreign keys) — SRS §2.4/§6.1.
- **Character set:** `utf8mb4`, collation `utf8mb4_0900_ai_ci` (case-insensitive, accent-insensitive —
  needed for `REQ-1.3` keyword search to be forgiving).
- **Money:** `DECIMAL(10,2)`, never `FLOAT`/`DOUBLE` — SRS §6.1, `03` §4.
- **Timestamps:** `DATETIME`, stored in UTC, named `created_at`/`updated_at`/`*_at` — SRS §6.1.
- **Keys:** every table has a surrogate `INT`/`BIGINT` `AUTO_INCREMENT` primary key, matching the ER
  diagram. Every FK relationship shown in the ER diagram is an actual `FOREIGN KEY` constraint — never
  an "implied" relationship enforced only in application code (SRS §6.1: "every stated relationship
  shall be enforced by a foreign key").
- **Normalization:** 3NF minimum. The one deliberate denormalization is `product_variant`'s derived
  stock-status — Phase 1 keeps `stock_quantity` as the single source of truth and derives
  In-Stock/Out-of-Stock at query time (`fn_is_variant_in_stock`, §3) rather than storing a redundant
  flag that could drift (SRS §5.5, REQ-5.4). Any future denormalization (e.g. a materialized
  `product.min_price` for catalog sort performance) must be documented here with the read/write
  tradeoff it's making.
- **Naming:** tables/columns `snake_case`, matching the ER diagram entity names lower-cased
  (`product_variant`, `order_item`, `stock_movement`). Stored objects prefixed by kind: `sp_` procedures,
  `fn_` functions, `trg_` triggers, `vw_` views.

## 2. No ORM — the raw SQL policy

- All SQL is hand-written and lives next to the Go code that runs it (each module's `mysql/` package),
  as either an inline string constant or a `.sql` file loaded at build time — never generated by a
  query builder or reflection-based mapper.
- **Every parameter is a placeholder (`?`), bound through `database/sql`/`sqlx` — never string-built.**
  This is the direct, structural answer to SRS §5.3's SQL-injection requirement:

  ```go
  // Correct — parameterized, safe regardless of what's in `email`
  row := db.QueryRowContext(ctx,
      `SELECT user_id, password_hash, role_id FROM user_account WHERE email = ?`, email)

  // Forbidden — never do this, even for a value that "can't" contain SQL
  q := fmt.Sprintf(`SELECT * FROM user_account WHERE email = '%s'`, email)
  ```

  This rule has no exceptions for "trusted" input (an admin-typed value, an internal ID) — the point of
  a structural rule is that it doesn't depend on judgment calls about what's trusted.
- **Prepared statements** are reused for hot-path queries (`db.PrepareContext` held on the repository
  struct) where it measurably helps; for most Phase-1-scale queries a plain parameterized `Query`/`Exec`
  is fine and preparing everything up front is unneeded ceremony.
- Multi-statement/dynamic SQL (`sql.Named`-built `WHERE` clauses for optional filters, e.g. catalog
  search with optional category filter) is built by **appending whole placeholder clauses**, never by
  interpolating a value:

  ```go
  where := "WHERE p.is_active = 1"
  args := []any{}
  if categoryID != nil {
      where += " AND pc.category_id = ?"
      args = append(args, *categoryID)
  }
  ```

## 3. Stored procedures — atomic, multi-row business transactions

Procedures are used exactly where the SRS requires atomicity that the database is better positioned to
guarantee than application code calling several statements (`06` §1's caveat). Three procedures cover
Phase 1:

### 3.1 `sp_place_order` — REQ-4.2, 4.6, 4.7, 4.9, 4.10, 4.11 (the centerpiece)

Called by `ordering.Service.PlaceOrder` **inside** a Go-managed transaction (`shared/dbx.WithTx`) —
the procedure does the row-locking and validation; the Go layer owns `BEGIN`/`COMMIT`/`ROLLBACK` so it
can also run the payment-authorization step *before* opening the transaction (REQ-4.8: no DB
transaction held open across an external call).

```sql
DELIMITER $$

CREATE PROCEDURE sp_place_order(
    IN  p_customer_id   INT,
    IN  p_items_json    JSON,       -- [{"variant_id":1,"quantity":2}, ...] — priced/validated by the app layer just before the call
    IN  p_delivery_mode ENUM('StorePickup','StandardDelivery'),
    IN  p_delivery_city_id INT,
    IN  p_delivery_address VARCHAR(255),
    IN  p_payment_method ENUM('COD','Card'),
    IN  p_idempotency_key VARCHAR(64),
    IN  p_tax_amount    DECIMAL(10,2),
    IN  p_delivery_fee  DECIMAL(10,2),
    OUT p_order_id      INT
)
BEGIN
    DECLARE v_existing_order_id INT DEFAULT NULL;
    DECLARE v_subtotal DECIMAL(10,2) DEFAULT 0;
    DECLARE v_variant_id INT;
    DECLARE v_qty INT;
    DECLARE v_price DECIMAL(10,2);
    DECLARE v_stock INT;
    DECLARE v_done INT DEFAULT 0;
    DECLARE v_estimated_days INT;

    -- REQ-4.9: idempotency — replaying the same key returns the original order, never a second one
    SELECT order_id INTO v_existing_order_id
    FROM `order` WHERE idempotency_key = p_idempotency_key AND customer_id = p_customer_id;

    IF v_existing_order_id IS NOT NULL THEN
        SET p_order_id = v_existing_order_id;
    ELSE
        -- Lock every affected variant row, in ascending variant_id order, so two concurrent
        -- checkouts covering the same variants can never deadlock each other (REQ-4.7).
        -- A locking cursor over the JSON input, ordered ascending, achieves this.
        BEGIN
            DECLARE cur CURSOR FOR
                SELECT jt.variant_id, jt.quantity
                FROM JSON_TABLE(p_items_json, '$[*]' COLUMNS (
                        variant_id INT PATH '$.variant_id',
                        quantity   INT PATH '$.quantity'
                     )) AS jt
                ORDER BY jt.variant_id ASC;
            DECLARE CONTINUE HANDLER FOR NOT FOUND SET v_done = 1;

            OPEN cur;
            read_loop: LOOP
                FETCH cur INTO v_variant_id, v_qty;
                IF v_done THEN LEAVE read_loop; END IF;

                SELECT price, stock_quantity INTO v_price, v_stock
                FROM product_variant WHERE variant_id = v_variant_id FOR UPDATE;   -- REQ-4.1, 4.7 lock

                IF v_stock < v_qty THEN
                    SIGNAL SQLSTATE '45000'
                        SET MESSAGE_TEXT = 'STOCK_EXCEEDED', MYSQL_ERRNO = 4001;   -- REQ-4.3: whole tx aborts
                END IF;

                UPDATE product_variant
                   SET stock_quantity = stock_quantity - v_qty
                 WHERE variant_id = v_variant_id;                                  -- trg_stock_nonnegative backstops this

                SET v_subtotal = v_subtotal + (v_price * v_qty);
            END LOOP;
            CLOSE cur;
        END;

        INSERT INTO `order` (customer_id, status, subtotal, tax_amount, delivery_fee, total_amount,
                              idempotency_key, created_at)
        VALUES (p_customer_id, 'Confirmed', v_subtotal, p_tax_amount, p_delivery_fee,
                v_subtotal + p_tax_amount + p_delivery_fee, p_idempotency_key, UTC_TIMESTAMP());
        SET p_order_id = LAST_INSERT_ID();

        -- order_item rows carry the price AS-CONFIRMED (REQ-4.10) — a later catalog price change
        -- must never alter the value of an order already placed.
        INSERT INTO order_item (order_id, variant_id, quantity, unit_price_at_order)
        SELECT p_order_id, jt.variant_id, jt.quantity, pv.price
        FROM JSON_TABLE(p_items_json, '$[*]' COLUMNS (
                variant_id INT PATH '$.variant_id', quantity INT PATH '$.quantity'
             )) AS jt
        JOIN product_variant pv ON pv.variant_id = jt.variant_id;

        -- REQ-5.5: every stock decrease is logged with the related order — including this
        -- automatic, order-driven one, not just manual staff adjustments (sp_adjust_stock, §3.2).
        -- acting_user_id is NULL here on purpose: this decrement wasn't a person's action, it was
        -- the system's, and stock_movement.acting_user_id is nullable precisely for this case
        -- (06-inventory-stock/plan.md §2).
        INSERT INTO stock_movement (variant_id, change_qty, reason, related_order_id, acting_user_id, created_at)
        SELECT jt.variant_id, -jt.quantity, 'Order placed', p_order_id, NULL, UTC_TIMESTAMP()
        FROM JSON_TABLE(p_items_json, '$[*]' COLUMNS (
                variant_id INT PATH '$.variant_id', quantity INT PATH '$.quantity'
             )) AS jt;

        -- Computed once into a variable — not just to avoid calling the function twice, but because
        -- REQ-6.6 (Store Pickup) uses a different rule than Main/Other City (REQ-6.2/6.3), and
        -- p_delivery_city_id is NULL for Store Pickup (no destination city collected at all — see
        -- 04-checkout-orders/plan.md §2 delivery.city_id being nullable). fn_estimate_delivery_days
        -- branches on p_delivery_mode internally so this call is correct for both modes.
        SET v_estimated_days = fn_estimate_delivery_days(p_delivery_mode, p_delivery_city_id, p_items_json);

        INSERT INTO delivery (order_id, mode, city_id, address, estimated_days, estimated_date)
        VALUES (p_order_id, p_delivery_mode, p_delivery_city_id, p_delivery_address,
                v_estimated_days, DATE_ADD(CURDATE(), INTERVAL v_estimated_days DAY));

        INSERT INTO payment (order_id, method, status, amount, created_at)
        VALUES (p_order_id, p_payment_method,
                IF(p_payment_method = 'COD', 'Pending', 'Paid'),   -- Card is authorized by the app before this call
                v_subtotal + p_tax_amount + p_delivery_fee, UTC_TIMESTAMP());

        -- REQ-8.5's "every status change" is logged by trg_order_status_history (§4) — but that's an
        -- AFTER UPDATE trigger, and this order's first status (Confirmed) is set by this INSERT, not
        -- an UPDATE, so the trigger never fires for it. Without this line an order's history would be
        -- missing its own starting point. changed_by_user_id is NULL: nobody "changed" it, the system
        -- created it (same reasoning as the stock_movement row above).
        INSERT INTO order_status_history (order_id, status, changed_by_user_id, changed_at)
        VALUES (p_order_id, 'Confirmed', NULL, UTC_TIMESTAMP());
    END IF;
END$$
DELIMITER ;
```

- On `SIGNAL '45000'` (`STOCK_EXCEEDED`), Go's driver surfaces a `*mysql.MySQLError` with that message;
  `mysql/` repository code maps it to a typed `app`-layer error, and `httpapi` maps that to HTTP `409`
  with the unavailable lines listed — the same error, translated once per layer, never a raw DB message
  reaching the client (`02` §4, `06` §5).
- The `FOR UPDATE` lock inside a `CONTINUE HANDLER`-guarded cursor, ordered by `variant_id`, is the
  concrete mechanism behind REQ-4.7's deadlock-avoidance requirement — worth being able to explain in a
  viva: two transactions locking rows 5 then 9 never meet a transaction locking 9 then 5, because both
  always lock in the same ascending order.

### 3.2 `sp_adjust_stock` — REQ-5.2, 5.5, 5.6

Manual staff stock adjustment; writes both the new quantity and a `stock_movement` audit row in one
statement group, and rejects a decrease that would go negative (REQ-5.6) with a clear signal rather
than silently clamping.

```sql
CREATE PROCEDURE sp_adjust_stock(
    IN p_variant_id INT, IN p_delta INT, IN p_reason VARCHAR(255), IN p_acting_user_id INT
)
BEGIN
    DECLARE v_stock INT;
    SELECT stock_quantity INTO v_stock FROM product_variant WHERE variant_id = p_variant_id FOR UPDATE;
    IF v_stock + p_delta < 0 THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'ADJUSTMENT_BELOW_ZERO', MYSQL_ERRNO = 4002;
    END IF;
    UPDATE product_variant SET stock_quantity = stock_quantity + p_delta WHERE variant_id = p_variant_id;
    INSERT INTO stock_movement (variant_id, change_qty, reason, acting_user_id, created_at)
    VALUES (p_variant_id, p_delta, p_reason, p_acting_user_id, UTC_TIMESTAMP());
END$$
```

### 3.3 `sp_cancel_order` — REQ-8.6

Returns reserved stock to every affected variant and appends the cancellation, in one transaction.

```sql
CREATE PROCEDURE sp_cancel_order(IN p_order_id INT, IN p_acting_user_id INT)
BEGIN
    UPDATE product_variant pv
    JOIN order_item oi ON oi.variant_id = pv.variant_id
    SET pv.stock_quantity = pv.stock_quantity + oi.quantity
    WHERE oi.order_id = p_order_id;

    -- REQ-5.5: the restock is logged too, not just the original decrement — acting_user_id is the
    -- staff member who cancelled the order (unlike sp_place_order's system-driven NULL, a
    -- cancellation is always a person's action, REQ-8.3).
    INSERT INTO stock_movement (variant_id, change_qty, reason, related_order_id, acting_user_id, created_at)
    SELECT oi.variant_id, oi.quantity, 'Order cancelled', p_order_id, p_acting_user_id, UTC_TIMESTAMP()
    FROM order_item oi WHERE oi.order_id = p_order_id;

    UPDATE `order` SET status = 'Cancelled' WHERE order_id = p_order_id;
    -- trg_order_status_history (§4) logs this transition automatically
END$$
```

All three run `SQL SECURITY INVOKER` (the app's low-privilege role must itself hold `UPDATE` on
`product_variant`/`order`/`INSERT` on `stock_movement`/`order_status_history` — see `02` §6.4). None
of them need elevated privilege beyond what the app role already has, so `INVOKER` is correct here.

## 4. Triggers — database-enforced backstops for rules that must never be bypassed

Triggers are used where a rule must hold **even if some future code path skips the service layer** —
defense in depth, not the primary mechanism (the primary mechanism is the Go `app`/`domain` layer and,
for stock, `sp_place_order` itself). Three triggers:

```sql
-- REQ-5.3: stock may never go below zero, no matter what statement caused the update.
-- Backstops sp_place_order's own check and sp_adjust_stock's own check.
CREATE TRIGGER trg_stock_nonnegative
BEFORE UPDATE ON product_variant
FOR EACH ROW
BEGIN
    IF NEW.stock_quantity < 0 THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'STOCK_CANNOT_BE_NEGATIVE';
    END IF;
END$$

-- REQ-8.2: only valid order-status transitions are ever committed, enforced at the row level —
-- independent of whatever the Go state-machine check already did (06 §1's "DB is the authority" case).
CREATE TRIGGER trg_order_status_transition
BEFORE UPDATE ON `order`
FOR EACH ROW
BEGIN
    IF OLD.status = 'Delivered' AND NEW.status NOT IN ('Delivered','Completed') THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'INVALID_STATUS_TRANSITION';
    END IF;
    IF OLD.status = 'Cancelled' AND NEW.status <> 'Cancelled' THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'ORDER_IS_TERMINAL';
    END IF;
END$$

-- REQ-8.5: every status change is recorded automatically — the app never has to remember to log it,
-- and can't forget to (which a purely application-side audit call could).
CREATE TRIGGER trg_order_status_history
AFTER UPDATE ON `order`
FOR EACH ROW
BEGIN
    IF NEW.status <> OLD.status THEN
        INSERT INTO order_status_history (order_id, status, changed_by_user_id, changed_at)
        VALUES (NEW.order_id, NEW.status, @acting_user_id, UTC_TIMESTAMP());
        -- @acting_user_id is set by the app with `SET @acting_user_id = ?` as the first statement
        -- of the same session/transaction — see mysql/ package's UpdateOrderStatus.
    END IF;
END$$
```

> The `@acting_user_id` session variable is a deliberate, documented pattern — MySQL triggers can't
> receive parameters, so "who made this change" has to arrive some way. The alternative (a nullable
> `changed_by_user_id` filled in by a second application `INSERT`, defeating the point of the trigger)
> was rejected because it re-introduces the "app can forget" failure mode the trigger exists to remove.

## 5. Functions — reusable scalar logic, callable from SQL and procedures

```sql
-- REQ-6.1: classify a city as Main or Other from the reference table, not a hard-coded list.
CREATE FUNCTION fn_classify_city(p_city_id INT) RETURNS ENUM('Main','Other') DETERMINISTIC
BEGIN
    DECLARE v_class ENUM('Main','Other');
    SELECT classification INTO v_class FROM city WHERE city_id = p_city_id;
    RETURN COALESCE(v_class, 'Other');
END$$

-- REQ-6.2, 6.3, 6.4, 6.6: mode-aware — Store Pickup (REQ-6.6) does NOT use the Main/Other City rule
-- at all, and p_city_id is NULL for it (no destination city is collected for pickup — 04-checkout-
-- orders/plan.md §2). Bug fixed 2026-09-04: an earlier draft called this with only (city_id, items)
-- regardless of mode, which would have run fn_classify_city(NULL) -> 'Other' -> 7 days for every
-- Store Pickup order. TBD-3 (10_BA_AUDIT_OPEN_QUESTIONS.md) is the working assumption for the
-- out-of-stock pickup case: same +3-day rule as Standard Delivery, base 0 instead of 5/7.
CREATE FUNCTION fn_estimate_delivery_days(
    p_delivery_mode ENUM('StorePickup','StandardDelivery'), p_city_id INT, p_items_json JSON
) RETURNS INT DETERMINISTIC
BEGIN
    DECLARE v_base INT;
    DECLARE v_any_out_of_stock INT;

    SELECT COUNT(*) INTO v_any_out_of_stock
    FROM JSON_TABLE(p_items_json, '$[*]' COLUMNS (variant_id INT PATH '$.variant_id')) AS jt
    JOIN product_variant pv ON pv.variant_id = jt.variant_id AND pv.stock_quantity = 0;

    IF p_delivery_mode = 'StorePickup' THEN
        RETURN IF(v_any_out_of_stock > 0, 3, 0);                    -- REQ-6.6 + TBD-3 assumption
    END IF;

    SET v_base = IF(fn_classify_city(p_city_id) = 'Main', 5, 7);    -- REQ-6.2
    RETURN v_base + IF(v_any_out_of_stock > 0, 3, 0);                -- REQ-6.3
END$$

-- REQ-5.4: derived, not stored — In Stock / Out of Stock is always computed from the live quantity.
CREATE FUNCTION fn_is_variant_in_stock(p_variant_id INT) RETURNS BOOLEAN DETERMINISTIC
BEGIN
    RETURN (SELECT stock_quantity > 0 FROM product_variant WHERE variant_id = p_variant_id);
END$$
```

## 6. Views — the five management reports (REQ-9.1–9.9), read-only by construction

`reporting`'s Go package issues a plain `SELECT * FROM vw_... WHERE ...` and nothing else — no report
query joins raw tables directly (`00` §3, `02` §6.3). Each view demonstrates a distinct advanced-SQL
technique, chosen because the report actually calls for it, not for coverage's sake.

```sql
-- REQ-9.1: quarterly sales, Q1–Q4 per year. WITH ROLLUP for a per-year grand-total row for free.
CREATE VIEW vw_quarterly_sales AS
SELECT YEAR(order_date) AS sales_year, QUARTER(order_date) AS sales_quarter,
       SUM(total_amount - tax_amount - delivery_fee) AS sales_value   -- REQ-9.7: excludes tax/delivery
FROM `order`
WHERE status <> 'Cancelled'                                            -- REQ-9.7
GROUP BY YEAR(order_date), QUARTER(order_date) WITH ROLLUP;

-- REQ-9.2: top-selling products, ranked two ways — RANK() over quantity and over revenue.
CREATE VIEW vw_top_selling_products AS
SELECT p.product_id, p.name,
       SUM(oi.quantity) AS total_quantity,
       SUM(oi.quantity * oi.unit_price_at_order) AS total_revenue,
       RANK() OVER (ORDER BY SUM(oi.quantity) DESC)                    AS rank_by_quantity,
       RANK() OVER (ORDER BY SUM(oi.quantity * oi.unit_price_at_order) DESC) AS rank_by_revenue
FROM order_item oi
JOIN product_variant pv ON pv.variant_id = oi.variant_id
JOIN product p           ON p.product_id = pv.product_id
JOIN `order` o            ON o.order_id = oi.order_id
WHERE o.status <> 'Cancelled'
GROUP BY p.product_id, p.name;

-- REQ-9.3: category-wise order counts. A CTE de-duplicates (order, category) pairs first so an
-- order spanning 3 categories counts once per category, never triple-counted — the SRS is explicit
-- that this column does not sum to the total order count, and this is exactly why.
CREATE VIEW vw_category_wise_orders AS
WITH order_categories AS (
    SELECT DISTINCT o.order_id, pc.category_id
    FROM `order` o
    JOIN order_item oi   ON oi.order_id = o.order_id
    JOIN product_variant pv ON pv.variant_id = oi.variant_id
    JOIN product_category pc ON pc.product_id = pv.product_id
    WHERE o.status <> 'Cancelled'
)
SELECT c.category_id, c.name, COUNT(oc.order_id) AS order_count
FROM category c
LEFT JOIN order_categories oc ON oc.category_id = c.category_id
GROUP BY c.category_id, c.name;

-- REQ-9.4: upcoming, unfulfilled orders with their estimated delivery date.
CREATE VIEW vw_upcoming_deliveries AS
SELECT o.order_id, cu.name AS customer_name, d.estimated_date, o.status
FROM `order` o
JOIN delivery d  ON d.order_id = o.order_id
JOIN customer cu ON cu.customer_id = o.customer_id
WHERE o.status NOT IN ('Delivered','Completed','Cancelled');

-- REQ-9.5: customer-wise order + payment summary.
CREATE VIEW vw_customer_order_summary AS
SELECT cu.customer_id, cu.name, o.order_id, o.order_date, o.status,
       o.total_amount, pay.method AS payment_method, pay.status AS payment_status
FROM customer cu
JOIN `order` o  ON o.customer_id = cu.customer_id
JOIN payment pay ON pay.order_id = o.order_id;
```

- REQ-9.9 (CSV export) is an application-layer concern (`reporting/httpapi` streams the view's result
  set as CSV) — not a database object.
- These five views are exactly the set of "advanced SQL" techniques the DBMS module asks for, applied
  because the report needs them: `WITH ROLLUP` for a subtotal-plus-grand-total report,
  window-function `RANK()` for a leaderboard-shaped report, a `CTE` for a correct de-duplication before
  aggregation, and plain joins where a report is genuinely just a join (forcing a window function or
  rollup into `vw_customer_order_summary` would be technique for its own sake, not because the report
  needs it — resist that temptation).

## 7. Indexing (SRS §6.1, minimum set)

| Table.column(s) | Type | Serves |
|---|---|---|
| `order_item.order_id`, `order_item.variant_id` | index (FK) | join cost in checkout, order detail, all report views |
| `product_variant.product_id` | index (FK) | product → variants lookup |
| `product_variant.sku` | **unique** | REQ-5.1, REQ-10.4 SKU uniqueness |
| `customer.email` (via `user_account.email`) | **unique** | REQ-2.2 |
| `order.order_date` | index | REQ-9.1/9.4 date-range reports |
| `order.customer_id` | index | REQ-8.4 own-order-history lookups (also the ownership-scoping filter, `02` §6.2) |
| `order.idempotency_key` | **unique** | REQ-4.9 |
| `product_category.product_id`, `product_category.category_id` | composite index (both directions) | catalog filter-by-category, `vw_category_wise_orders` |
| `permission.code` | **unique** | `RequirePermission(code)` lookups at seed/admin-edit time (§1a) |

Every index here exists because a specific query above needs it — add new indexes the same way
(name the query it serves), not speculatively.
